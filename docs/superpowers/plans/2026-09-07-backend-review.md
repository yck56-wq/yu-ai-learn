## 已修复：同一用户不同轮次并发结算发生死锁（P2）

位置：`backend/app/repositories/quiz_repository.py:26-36`，原实现先插入 `answer_records` 和 `reports`，最后更新 `users.total_xp`。

两个请求分别锁定不同题库行后，插入带有 `users` 外键的子记录都会取得同一用户行的共享锁；随后两个事务更新 XP，都需要将共享锁升级为独占锁，形成死锁。其中一个有效结算请求因此返回 503。

主代理通过 `test_two_different_rounds_can_settle_concurrently_without_deadlock` 在两个 XP 更新前设置同步屏障，确认旧顺序失败。现代码先在同一事务内原子更新 XP，取得用户行写锁后再插入两张子表，消除了此共享锁升级环路。题库行锁和“已有报告直接返回”的顺序保留，同轮幂等不受影响；后续插入失败仍由事务整体回滚 XP。

主代理报告以下三项针对性测试均通过：不同轮次并发结算、同轮重复与并发幂等、报告插入失败时答案与 XP 全部回滚。审核代理已直接读取修复代码及新增测试，未并行重复运行测试，以免干扰共享测试库。

## 其余核查

- JWT 固定 HS256，检查必要声明、有效期、用户 ID 类型及账号存在性；业务接口通过依赖先鉴权再调用模型。
- 微信错误和数据库错误使用固定响应，输出不包含上游凭证；生产启动拒绝过短 JWT 签名密钥。
- 判题、题目覆盖及选项校验使用数据库快照，客户端题目、主题和自行填写的正确标记不能改变结算成绩。
- 题库落库成功才返回；整轮答案、报告和每题 20 XP 使用同一连接及事务，重复提交返回已保存报告。
- 历史和详情按用户归属且仅查询已有报告轮次；档案正确率按累计答对数除以累计题数计算，列表保留两位小数，报告整数正确率沿用原接口。
